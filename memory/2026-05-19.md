## 设计服务端核心领域模型

- 产出：`outputs/server_domain_model_design.md`。
- 主要设计：采用 `GameState` 作为权威状态；客户端动作抽象为 `PlayerCommand`；事实变更统一为 `GameEvent`；响应窗口统一为 `PendingAction`；常规技能和人物技能统一为 `SkillDefinition`；死亡、胜利分别由 `DeathEngine` 与 `WinEngine` 处理。
- 模块边界：建议拆分为 `domain/`（类型与状态）、`engine/`（FSM、Reducer、事件总线、技能、死亡、胜利、身份、情报）、`skills/`（常规技能与人物技能）、`transport/`（WebSocket JSON DTO 映射）。
- 关键原则：技能不写死在主流程中，所有状态变更通过事件；死亡优先于胜利由统一结算队列保证；白方任务保留接口但 Milestone 1 不启用。

- 建议：下一步任务“设计阶段 FSM 与事件队列”可直接基于本设计细化 `fsm.ts`、`event-bus.ts`、`reducer.ts` 的状态推进算法。

## 设计阶段 FSM 与事件队列
- 任务：`设计阶段 FSM 与事件队列`（task-1779174759794-8kppy7）。
- 输入：读取 `outputs/mvp_rule_checklist.md`、`outputs/server_domain_model_design.md`，并基于已有 `outputs/fsm_event_queue_design.md` 完成设计确认与记录。
- 产出：`outputs/fsm_event_queue_design.md`。
- 主要设计：阶段主流程固定为 `Lobby → Setup → VictoryDeclareWindow → SkillWindow → TransferDeclare → ReactionWindow → ReceiveDecision/InfoSettle → DyingWindow/DeathSettle → TurnEnd → VictoryDeclareWindow`；宣胜只在 `VictoryDeclareWindow` 由玩家确认，WinEngine 只生成候选不直接结束游戏。
- 事件队列方案：拆分 `commandQueue`、`eventQueue`、`settlementQueue` 三层；玩家命令只产生领域事件，事件由 reducer 应用后再通过 EventBus 触发技能、死亡、胜利候选与阶段推进；所有 settlement job 必须在下一条玩家命令前清空，除非正在等待阻塞型 PendingAction。
- PendingAction 方案：统一承载宣胜、常规技能、接收/拒收、濒死技能、后续人物技能窗口；默认策略为所有 eligible 玩家 act/pass 后关闭，便于测试与回放。
- 关键规则落点：截获解析优先于锁定；死亡队列和濒死窗口永远优先于胜利确认；`DeclareVictoryCommand` 必须校验无未结算死亡和无濒死玩家。
- 发现/问题：仍需产品确认是否允许非当前玩家在技能阶段主动试探、多人响应最终采用座位顺序还是服务端收到顺序、是否需要在换人前补独立的 `PostTransferSkillWindow`。
- 建议：下一步“搭建 TypeScript WebSocket MVP 项目骨架”可直接按本设计拆分 `domain/phase.ts`、`domain/event.ts`、`domain/pending-action.ts`、`engine/fsm.ts`、`engine/event-bus.ts`、`engine/reducer.ts` 等文件。
