# 2026-05-21 进展记录

## 重连后房间不存在问题修复

### 用户反馈
- 创建好房间后，离开/刷新浏览器会显示“重新连接”，随后提示“房间不存在”。

### 根因分析
1. **持久化存在 30 秒窗口**：房间状态原本每 30 秒自动保存一次；如果刚创建房间后服务因部署更新、重启或异常退出，房间可能还没写入 `data/rooms.json`，重启后自然查不到。
2. **客户端旧房间记录反复重试**：当服务端确认 `room.notFound` / `reconnect.seatNotFound` / `sync.notInRoom` 后，客户端仍可能保留旧 roomId，继续 requestSync/reconnect，导致用户不断看到“房间不存在”。

### 修复内容
- 服务端新增 `persistNow()`，并在 `broadcastRoom()` 后立即保存所有房间状态。
- 创建房间、加入房间、准备、断线状态、房主转移等所有会 broadcast 的变更现在都会即时落盘，不再等待 30 秒。
- 客户端新增 `WsClient.forgetRoom()`，清除本机保存的 roomId、重连标志以及 pending 的 requestSync/reconnect/房间命令。
- App 收到 `room.notFound`、`reconnect.seatNotFound`、`sync.notInRoom` 时自动清空当前房间视图和本地房间记录，提示用户原房间已不存在。

### 验证
- `npm run typecheck` ✅
- `npm test` ✅（3 个测试文件，71 个测试）
- `npm run build` ✅

## 创建房间后立即显示重连并房间消失二次修复

### 用户反馈
- 创建好房间后页面马上显示“重新连接”，随后提示“房间不存在”。

### 新根因分析
1. **App 的 WebSocket 订阅 effect 依赖 `pendingLabels`**：每次提交创建房间/收到 ACK 都会触发 effect 清理并重新订阅；清理函数解绑了 status handler，重新订阅时会立刻收到当前 `closed/reconnecting` 状态，导致 UI 在刚创建房间后误进入重连提示。
2. **requestSync 可能早于 reconnect/roomView 结算**：重连中如果 pending 的 `requestSync` 先发送，服务端可能按新临时 userId 判定 `sync.notInRoom`，客户端又把房间记录清掉，造成“房间不存在”的假象。
3. **客户端对 `room.notFound/sync.notInRoom` 过度清房间**：这些错误在重连竞态中可能是临时同步失败，不应该直接清掉本地 roomId；只有 `reconnect.seatNotFound` 才说明座位恢复失败。

### 修复内容
- App 使用 `pendingLabelsRef` 存操作反馈映射，`useEffect` 依赖改为 `[client]`，避免每次 pendingLabels 变化重建 WebSocket 订阅。
- App 增加 `activeRoomIdRef`，创建/加入/收到 roomView 时立即记录当前房间，open 后同步优先使用 ref 中房间号。
- `WsClient` 在 `reconnectInFlight` 期间暂停 `requestSync` 和 pending 消息刷新，等收到 `roomView` 后再 flush，避免同步请求抢跑。
- 客户端只在 `reconnect.seatNotFound` 时清除本地房间记录，不再因普通 `room.notFound` / `sync.notInRoom` 直接清房间。
- 持久化写盘过滤 closed 房间，避免关闭房间继续落盘恢复。

### 验证
- `npm run typecheck` ✅
- `npm test` ✅（3 个测试文件，71 个测试）
- `npm run build` ✅

## 打开网页即提示“房间不存在”修复

### 用户反馈
- 不创建房间，只是打开网页就出现错误：“房间不存在”。

### 根因分析
- 浏览器 localStorage 中仍保存着旧 `roomId`。
- 页面初始化后会按本地 `roomId` 自动 `requestSync`。
- 如果服务端已清理/未恢复该旧房间，就会返回 `room.notFound`。
- 这是本机缓存旧房间导致的正常恢复失败，不应该作为红色错误弹给用户。

### 修复内容
- App 新增 `currentRoomRef` 与 `lastRejectedCodeRef`：区分“当前真的在房间里出错”和“页面刚打开恢复旧房间失败”。
- 当页面刚打开且没有当前房间时，收到 `room.notFound` / `sync.notInRoom` 会静默 `client.forgetRoom()` 并清空房间输入框，不再弹错误。
- `reconnect.seatNotFound` 仍会提示“座位不存在并清除本机记录”，但避免 commandRejected + error 双重弹窗。

### 验证
- `npm run typecheck` ✅
- `npm test` ✅（3 个测试文件，71 个测试）
- `npm run build` ✅

## 创建房间后仍显示“正在重新连接”修复

### 用户反馈
- 打开网页后点击创建房间，房间创建成功但页面仍显示“正在重新连接”，随后可能被旧房间恢复失败响应干扰。

### 根因分析
- 浏览器 localStorage 中的旧 `userId/roomId` 会让 WebSocket 打开后先进入 `reconnectInFlight`。
- 用户此时主动创建/加入新房间后，旧房间的 `reconnect.seatNotFound` 响应可能晚于新房间创建成功到达。
- App 原先会把这个迟到的旧房间错误当成当前房间错误处理，显示重连/房间不存在，甚至清理新房间状态。

### 修复内容
- `WsClient.send()` 在用户主动 `CreateRoom` / `JoinRoom` 时结束旧 `reconnectInFlight`，并移除 pending 中的旧 `requestSync/reconnect`。
- 收到 `reconnect.seatNotFound` 后只清理旧 requestSync/reconnect 队列，再 flush 其他真实用户操作。
- App 在 `roomCreated` / `joinedRoom` 后设置 3 秒保护窗口，忽略旧房间恢复失败的迟到 `commandRejected/error`。
- App 若当前已有 `roomView`，也不会因迟到的旧 `reconnect.seatNotFound` 清掉当前房间。

- `npm run typecheck` ✅
- `npm test` ✅（3 个测试文件，71 个测试）
- `npm run build` ✅
