# 2026-05-21 进展记录

## 持久化目录无权限导致服务崩溃（重连Bug根因）

### 用户反馈
- 所有人只要点击创建房间，就会显示重新连接，然后别人输入房间号也无法加入房间。
- 之前以为是前端竞态条件，排查并移除预发 hello 后，问题依旧。

### 根因分析
- 获取到服务端 `journalctl` 日志后，真相大白：
  ```text
  [persistence] 30s : EACCES: permission denied, mkdir '/opt/wujianfengyun/data'
  wujianfengyun-server.service: Main process exited, code=exited, status=1/FAILURE
  ```
- 每次创建房间后立即触发 `persistNow()` 落盘。
- `initPersistence()` 尝试 `fs.mkdirSync(DATA_DIR)` 创建 `/opt/wujianfengyun/data` 目录。
- 由于 Ubuntu 服务器中执行服务的账户没有 `/opt/wujianfengyun/` 的写入权限，抛出未捕获的 `EACCES` 异常。
- 整个 Node.js 服务端进程崩溃退出。
- 导致所有客户端 WebSocket 瞬间断开，前端 UI 显示“正在重连”。
- Systemd 在 3 秒后重启了服务。
- 前端自动重连上新进程后，因为房间在崩溃前没来得及落盘保存，新进程内存是空的，服务端返回 `room.notFound`。
- 这完美解释了为什么“所有人一点建房就重连，随后提示房间不存在，别人也进不去”。

### 修复内容
- 后端：在 `server/src/engine/persistence.ts` 中的 `initPersistence` 里加入 `try/catch`，防止目录创建权限失败直接导致整个进程崩溃退出。
- 运维层：告知用户在服务器执行：
  ```bash
  sudo mkdir -p /opt/wujianfengyun/data
  sudo chmod 777 /opt/wujianfengyun/data
  ```

### 验证
- 代码已提交并推送到 `main`。
- 本地 typecheck、test 均通过。

## 重连后房间不存在问题修复

### 用户反馈
- 创建好房间后，离开/刷新浏览器会显示“重新连接”，随后提示“房间不存在”。

### 根因分析
1. **持久化存在 30 秒窗口**：房间状态原本每 30 秒自动保存一次；如果刚创建房间后服务因部署更新、重启或异常退出，房间可能还没写入 `data/rooms.json`，重启后自然查不到。
2. **客户端旧房间记录反复重试**：当服务端确认 `room.notFound` / `reconnect.seatNotFound` / `sync.notInRoom` 后，客户端仍可能保留旧 roomId，继续 requestSync/reconnect，导致用户不断看到“房间不存在”。

### 修复内容
- 服务端新增 `persistNow()`，并在 `broadcastRoom()` 后立即保存所有房间状态。
- 创建房间、加入房间、准备、断线状态、房主转移等所有会 broadcast 的变更现在都会即时落盘，不再等待 30 秒。
- 客户端新增 `WsClient.forgetRoom()`，清除本机保存的 roomId、重连标志以及 pending 的 requestSync/reconnect/房间命令。
- App 收到 `room.notFound`、`reconnect.seatNotFound`、`sync.notInRoom` 时自动清空当前房间视图和本地房间记录，提示用户原房间已不存在。

### 验证
- `npm run typecheck` ✅
- `npm test` ✅（3 个测试文件，71 个测试）
- `npm run build` ✅

## 创建房间后立即显示重连并房间消失二次修复

### 用户反馈
- 创建好房间后页面马上显示“重新连接”，随后提示“房间不存在”。

### 新根因分析
1. **App 的 WebSocket 订阅 effect 依赖 `pendingLabels`**：每次提交创建房间/收到 ACK 都会触发 effect 清理并重新订阅；清理函数解绑了 status handler，重新订阅时会立刻收到当前 `closed/reconnecting` 状态，导致 UI 在刚创建房间后误进入重连提示。
2. **requestSync 可能早于 reconnect/roomView 结算**：重连中如果 pending 的 `requestSync` 先发送，服务端可能按新临时 userId 判定 `sync.notInRoom`，客户端又把房间记录清掉，造成“房间不存在”的假象。
3. **客户端对 `room.notFound/sync.notInRoom` 过度清房间**：这些错误在重连竞态中可能是临时同步失败，不应该直接清掉本地 roomId；只有 `reconnect.seatNotFound` 才说明座位恢复失败。

### 修复内容
- App 使用 `pendingLabelsRef` 存操作反馈映射，`useEffect` 依赖改为 `[client]`，避免每次 pendingLabels 变化重建 WebSocket 订阅。
- App 增加 `activeRoomIdRef`，创建/加入/收到 roomView 时立即记录当前房间，open 后同步优先使用 ref 中房间号。
- `WsClient` 在 `reconnectInFlight` 期间暂停 `requestSync` 和 pending 消息刷新，等收到 `roomView` 后再 flush，避免同步请求抢跑。
- 客户端只在 `reconnect.seatNotFound` 时清除本地房间记录，不再因普通 `room.notFound` / `sync.notInRoom` 直接清房间。
- 持久化写盘过滤 closed 房间，避免关闭房间继续落盘恢复。

### 验证
- `npm run typecheck` ✅
- `npm test` ✅（3 个测试文件，71 个测试）
- `npm run build` ✅

## 打开网页即提示“房间不存在”修复

### 用户反馈
- 不创建房间，只是打开网页就出现错误：“房间不存在”。

### 根因分析
- 浏览器 localStorage 中仍保存着旧 `roomId`。
- 页面初始化后会按本地 `roomId` 自动 `requestSync`。
- 如果服务端已清理/未恢复该旧房间，就会返回 `room.notFound`。
- 这是本机缓存旧房间导致的正常恢复失败，不应该作为红色错误弹给用户。

### 修复内容
- App 新增 `currentRoomRef` 与 `lastRejectedCodeRef`：区分“当前真的在房间里出错”和“页面刚打开恢复旧房间失败”。
- 当页面刚打开且没有当前房间时，收到 `room.notFound` / `sync.notInRoom` 会静默 `client.forgetRoom()` 并清空房间输入框，不再弹错误。
- `reconnect.seatNotFound` 仍会提示“座位不存在并清除本机记录”，但避免 commandRejected + error 双重弹窗。

- `npm run typecheck` ✅
- `npm test` ✅（3 个测试文件，71 个测试）

## 创建房间后仍显示“正在重新连接”修复

### 用户反馈
- 打开网页后点击创建房间，房间创建成功但页面仍显示“正在重新连接”，随后可能被旧房间恢复失败响应干扰。

### 根因分析
- 浏览器 localStorage 中的旧 `userId/roomId` 会让 WebSocket 打开后先进入 `reconnectInFlight`。
- 用户此时主动创建/加入新房间后，旧房间的 `reconnect.seatNotFound` 响应可能晚于新房间创建成功到达。
- App 原先会把这个迟到的旧房间错误当成当前房间错误处理，显示重连/房间不存在，甚至清理新房间状态。

### 修复内容
- `WsClient.send()` 在用户主动 `CreateRoom` / `JoinRoom` 时结束旧 `reconnectInFlight`，并移除 pending 中的旧 `requestSync/reconnect`。
- 收到 `reconnect.seatNotFound` 后只清理旧 requestSync/reconnect 队列，再 flush 其他真实用户操作。
- App 在 `roomCreated` / `joinedRoom` 后设置 3 秒保护窗口，忽略旧房间恢复失败的迟到 `commandRejected/error`。
- App 若当前已有 `roomView`，也不会因迟到的旧 `reconnect.seatNotFound` 清掉当前房间。

### 验证
- `npm run typecheck` ✅
- `npm test` ✅（3 个测试文件，71 个测试）

## 所有人点击创建房间均显示重连的再次修复

### 用户反馈
- 所有人只要点击“创建房间”，都会显示正在重新连接。

### 新根因分析
- `createRoom()` / `joinRoom()` 会先发送 `hello` 再发送 `CreateRoom` / `JoinRoom`。
- 如果浏览器 localStorage 中有旧 `userId/roomId`，WebSocket 打开时会自动发送旧 `reconnect`；同时手动 `hello` 与 `CreateRoom` 又进入同一连接，造成“旧房间恢复”和“新建房间”并发。
- `send()` 虽然在发送 `CreateRoom` 时会取消旧 `reconnectInFlight`，但无法阻止当前连接 open 阶段已经发出的旧 `reconnect`，因此 UI 仍可能进入 reconnecting 或收到旧房间失败响应。

### 修复内容
- `App.createRoom()` / `joinRoom()` 不再预发 `hello`，直接由 `CreateRoom` / `JoinRoom` 携带昵称。
- `WsClient` 新增 `suppressReconnectOnNextOpen`：主动创建/加入新房间时，下一次 socket open 跳过旧房间自动 reconnect，先发普通 hello 并 flush 新房间命令。
- `WsClient.cancelStaleReconnect()` 会清除重连定时器、重置重连次数；如果 socket 已经 open，立即把状态恢复为 `open`，避免 UI 长时间停留在“正在重连”。

### 验证
- `npm run typecheck` ✅
- `npm test` ✅（3 个测试文件，71 个测试）

## 机器人响应卡住与 GM 强制结束修复

### 用户反馈
- 与机器人对局时，机器人无法默认选择“不响应”，对局卡在响应窗口。
- 用户也无法强制结束游戏。

### 根因分析
- `openPendingAction` 原先先用旧 phase 创建 pending action，再进入 `ReactionWindow`，导致响应窗口的 pending action 仍挂在 `TransferDeclare` 阶段；机器人自动响应逻辑查找 `phase === ReactionWindow` 的动作时找不到。
- 机器人自动响应只在 `runBotAutoplay()` 循环中处理，若 pending action 创建时阶段不匹配，就无法完成默认跳过。
- 客户端只有 GM 强制推进，没有强制结束游戏入口。

### 修复内容
- `handleDeclareTransfer` 改为先进入 `ReactionWindow`，再创建响应窗口 pending action。
- 新增 `autoPassBotResponses()`：创建待响应窗口时立即让机器人自动 pass，并在 `maybeResolveReaction()` 中兜底再次处理。
- 新增 `GmForceEnd` 房间命令与 `forceEndGame()`，房主可直接强制结束对局。
- 游戏内房主工具条新增“强制推进阶段”和“强制结束游戏”。
- 日志补充 `bot.autoPass`、`gm.forceEnd` 等中文模板。
- 新增测试覆盖机器人响应窗口自动 pass 与 GM 强制结束。

### 验证
- `npm run typecheck` ✅
- `npm test` ✅（3 个测试文件，73 个测试）
